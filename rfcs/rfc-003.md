## Charter alignment

**Cell(s):** cell:portability, cell:reference, cell:identity, cell:conformance, cell:versioning
**Decision mode:** complex

Revisions 6–9 were complicated (rules: cell citation, governing preference, past-decision search). Revision 10's core-package exception touches four cells across two columns and is decided by the geometry below, so the RFC as accepted is complex.

**Governing cell preference:**
- Portability: *preserve over recognize* (`rfc-decision-cce3c00e`, `rfc-decision-8948e43f`). Aligned: a whole-package export carries every definition the package holds, unchanged, with its identity, so the package can be rebuilt elsewhere; nothing is re-derived on the far side.
- Identity: *identifier over label*. Aligned: the bundle's package identity is the source manifest's `id` and `version`, and every definition keeps its `id`, `namespace`, `name` and `version` ([C3], [C4]); the labels travel beside the identifiers and never replace them.
- Conformance: *one way over many*. Aligned: one artifact for a package in transit (the Package Bundle, one file form `.srspkg`); one closure rule, the reference strengths the standard already declares (`rfc-decision-c8704763`), rather than the per-kind closure list Revision 5 carried; one determinism rule.
- Versioning: *increment over edit*. Aligned: a later export of the same package is the same `packageId` at a higher `packageVersion`; definition versions are never rewritten on export.
- Reference: *declared strength over convenient reach* (`rfc-decision-c8704763`). Aligned: export follows exactly the PINNED and LINEAGE sites, never every string that happens to match an id.

**Geometry of the core-package exception (Revision 10, complex; `rfc-decision-a8dcbfe5`).** The question: in a `mode: "bundled"` export, are definitions of the RFC-029 core package, which every implementation embeds, carried like any other reached definition? Three options were plotted.

| Option | Portability (♓, preserve over recognize) | Attribution (♋, stated over assumed) | Reference (♎, declared strength) | Identity (♉, identifier over label) |
|---|---|---|---|---|
| Carry core definitions (Revision 9 literal) | met | met | met | met; but every bundle repeats the substrate and a consumer must deduplicate it on every install |
| Omit core, `dependencyRefs: []` (srs-rust#1210 as merged) | met only by assumption | **violated**: the dependency is assumed, never stated | **violated**: followed references are dropped | met |
| **Omit core from the arrays, list every reached core version in `dependencyRefs` (ruled)** | met by declaration: core is substrate every implementation embeds and is identical by `id` and `version` everywhere, so naming it preserves it | met: each core dependency is stated | met: the closure is unchanged, only what is carried differs | met: a core definition is named by `id` and `version`, never by label |

Column coherence: the Water column (Attribution, Assertion, Portability) reads *connection is explicit and carried, never implied or dropped*; the ruled option carries the connection as a `dependencyRefs` entry rather than as the definition's bytes, so no connection is dropped. The Earth column's fatal-identity rule is untouched: a core definition is identical by `id` and `version` in every implementation, so omitting its bytes cannot hide an identity conflict, and two different definitions with the same `id` and `version` still stop the export. Axis 6–12 (Portability over Possession) holds: the bundle never depends on anything only one place possesses. Emergence: the six Package invariants were written assuming bundled means "everything carried"; they gain the same stated exception, so the canonical floor and the export rule say one thing (Conformance, one way over many).

**Axis preference:**
- 6–12 Containment/Portability: default pole (Portability over Possession) taken. A package that can be installed but not exported is the "capability that exists only in place" the boundary clause calls captivity; this RFC is that package's travelling form, as `rfc-decision-8948e43f` mandates.
- 5–11 Succession/Conformance: default pole (Reliability over Renewal) taken. Boundary clause: *"Standing contracts hold; renewal only as explicit supersession at a declared boundary."* The standing contracts are RFC-044 [R5] ("RFC-003 `[C3]`") and RFC-045 Change B and [R3] ("`[C5]`", "RFC-003 whole-package export"), both owner-accepted. They are kept true by accepting the subset under RFC-003's own number and rule labels; the parts that move do so to a new Draft number that no accepted rule cites.
- 2–8 Identity/Assertion: default pole (Evolution over Continuity) taken; it changes nothing here, because no stored data changes (What breaks). The axis is phase-bound to flip to Continuity at the first full public release; these rules already sit on the Continuity side (identity is preserved, never rewritten), so the flip leaves them valid.
- 1–7 Versioning/Reference: default pole (Semantic Integrity over Practical Expression) taken: definition identity is never rewritten to suit a consumer.

**Decisions consulted:** `rfc-decision-cce3c00e` (grid), `rfc-decision-16b20c56` (Attribution: stated over assumed), `rfc-decision-d5524758` (RFC-046, revision 9; no bundle shape changes), `rfc-decision-8948e43f` (what a container can hold, a bundle can carry), `rfc-decision-4f1e12e5` and `rfc-decision-5f18603e` (federation entities including a registry removed, return committed; the `ext:registry` extension record is still live, but registry distribution is outside this subset), `rfc-decision-c8704763` (reference taxonomy; definition References are PINNED), `rfc-decision-2e0cd70a` (schemas closed, engines tolerant; DETECT/LOAD/WRITE), `rfc-decision-628cf6c4` (one name; a rename is a migration), `rfc-decision-c20fcff8` (the level test), `rfc-decision-9ee14517` and `rfc-decision-0118e938` (layer rules), `rfc-decision-7caca3a1` (decision modes), `rfc-decision-e99a9437` (doors), `rfc-decision-4431046e` (corrections and refinements), and RFC-044's successor decision `rfc-decision-aee09992` (requirements keyed by `packageId`; on srs PR #860). **Contradictions found:** None with a decision record. One naming collision is found and routed to the owner (resolved Open Question 1: a follow-up migration, srs#872): RFC-033 and RFC-029 describe the embedded core and metamodel package as a "deterministic `.srsj` bundle" valid against `package-bundle.json`, while `.srsj` is the `ext:json-store` repository format and this RFC names the Package Bundle's file form `.srspkg`. One name, two meanings (Description cell, `rfc-decision-628cf6c4`). This RFC does not rename that file (it is not produced by package export, and [C5]'s suffix rule binds export output only); the rename is the owner's call.

**One-way-per-goal:** The goal is "move a package's definitions out of one repository and into another". One mechanism exists for the install half (`install_package_bundle`, consuming `package-bundle.json`); this RFC defines the export half over the same artifact, not a second format. Within the RFC, Revision 5's per-kind closure list (a second, already stale statement of what a package depends on) is collapsed onto the reference strengths, which every definition schema already declares; the Package invariants check a subset of the same references and stay the checked floor ([C1]). The `.srsj` repository bundle (`ext:json-store`) and the `.srs` archive (RFC-017) serve a different goal (moving a repository's content, not a package's definitions) and are not touched. The partial-acceptance mechanics themselves add no mechanism: they reuse the two ways this repository has already moved scope between RFCs (Revision 5's pointer stubs, RFC-014's extraction under a new number).

**Layer test:**
- Which layer owns this? MEANING plane, definitions layer: the Package Bundle is the travelling form of a Package, the definitions grouping construct, and its shape is `package-bundle.json`. Export and install are OPERATION plane, core service (one `srs-repository` capability, exposed through CLI payload and WASM per `capability-layering.md`); clients add presentation only.
- Consume or clone downward? Consume. The closure consumes the declared reference strengths of the definition schemas; identity consumes the package manifest's `id`/`version`/`namespace`/`name` and RFC-044's `packageDependencies`; the revision gate consumes RFC-033 [R6] and RFC-043 [R17]. Nothing is restated as a new mechanism.
- Does the layer below stand alone without this? Yes. Delete this RFC and a package directory, its manifest, its definitions and every repository that installs it remain complete and valid; only the travelling form is lost.

**Level test (`rfc-decision-c20fcff8`):** passes. Every rule is checkable on an artifact or an operation: [C1] by validating the bundle against the schema and resolving every PINNED and LINEAGE reference site inside it (or in `dependencyRefs`); [C2] by inspecting its keys; [C3] and [C4] by comparing with the source package manifest; [C5] by exporting twice and comparing bytes, and by reading key and array order off any one bundle; [C6] by offering a reader a bundle stamped above and below its revision.

## Abstract

`.srspkg` files and `package-bundle.json` are already the format that srs-rust's package exporter (srs-rust#632) and muDemocracy.org#242's editor are about to build on, and RFC-044 and RFC-045 have already changed the bundle's shape, but the rules that say what a package export produces live in a Draft RFC. This revision narrows RFC-003 to exactly **whole-package export**, so it can be accepted: exporting an installed package writes one deterministic, sorted-key JSON file with the `.srspkg` suffix, in the `package-bundle.json` shape, carrying every definition of that package under the package's own `id` and `version` and never any records. Everything else RFC-003 proposed (subset export, registry distribution, entry points, binding, conflict records) moves unchanged to RFC-047, which stays Draft. **What acceptance does:** RFC-003 becomes Accepted with exactly Change C and [C1]–[C6]; RFC-047 stays Draft and binds nothing. Revision 10 is the accepted text: it adds the owner's core-package exception (srs#869) and the revival corrections listed in its history row.

### What you commit to, and what this forecloses

- **Committed:** a package export is a Package Bundle, one JSON document, suffix `.srspkg`, never a directory, a ZIP or a repository ([C1], [C2], [C5]).
- **Committed:** a whole-package export keeps the package's identity (`packageId` = the manifest's `id`, `packageVersion` = its `version`), so the next export of the same package is recognisably a newer version of it, and every definition keeps its own identity ([C3], [C4]).
- **Committed:** a bundled export is self-contained for every PINNED and LINEAGE reference (types, fields, views, vocabularies, lifecycles), except definitions of the RFC-029 core package, which every implementation embeds: those are listed in `dependencyRefs`, never carried ([C1]). Relation-type keys and Theme locators from other packages are not carried and resolve in the consumer, as for any package ([C1]).
- **Committed:** an export either writes a complete, valid bundle or writes nothing ([C1]).
- **Committed:** the same exporter build, given the same input, writes the same bytes; two different exporters write the same JSON value with the same member order and may differ in whitespace, string escapes and number spelling ([C5]).
- **Committed:** a reader never reads definitions from a bundle of a data-model revision it does not support; an older bundle is migrated first, a newer one is refused ([C6]).
- **Foreclosed:** carrying records, relations or source documents in a package export (use a container slice, RFC-026); an archive wrapper around a `.srspkg`; minting a new `packageId` on a whole-package export; reading a `.srspkg` as a repository.
- **Not decided here (RFC-047):** subset export and its new-`packageId` rule; `ext:registry` catalog entries (`downloadUrl`, `sha256`); `entryRefs`; `ConflictRecord`; `ext:binding`.

## Motivation

### Problem 1 — The format in use has no accepted home

`docs/schema/2.0/package-bundle.json` is a committed schema, RFC-044 (accepted) amended it, and RFC-045 (owner-accepted) adds `readme` to it. But the rules that say *what a package export produces* (one file, which suffix, which identity, which definitions, how deterministic) exist only in RFC-003 Revision 5, which is Draft. RFC-044 [R5] and RFC-045 [R3] both say their bundle-producer rules take effect "when RFC-003's whole-package export is accepted (srs#857)", and srs-rust#632 (the `srs package export` command) is next in the implementation queue (story muDemocracy.org#242). Building an exporter against a Draft RFC means building against a proposal that can still change under it.

### Problem 2 — An RFC has one status

RFC-003 Revision 5 bundles five unrelated proposals: a clarification of what a Package is (Change A), entry points (Change B), package export (Change C, both whole-package and subset, plus registry distribution and `ConflictRecord`), `ext:binding` (Change D) and distribution guidance (Change G). Only whole-package export is needed now and ready. The RFC record's status is one `spec-rfc-process` Lifecycle state, `check-rfc-integration.mjs` requires the `.md` Status line to equal it, and an RFC whose state is `accepted` must declare an integration manifest for what it folded. So an RFC cannot be "Accepted in part": the subset must be the whole of some RFC.

### Problem 3 — Revision 5's rules are not testable as written

`[C5]` says the serialisation is "sorted-key" and "byte-for-byte reproducible" but not which keys are sorted (top level, or every object), in what order, what order the definition arrays take, or what counts as "identical content" (an export stamps `publishedAt`). `[C1]` requires "the transitive dependency closure" and Revision 5 lists closure rules per definition kind, which restate part of what Invariants 7, 8, 15, 35, 36, 37 and 43 check and name constructs that have since been renamed or retired (`DocumentView`, `Schema`). The Distribution bullet points `[C5]`'s artifact at `ext:registry` fields that are not part of the subset.

## Proposed Changes

### Change C — Whole-package export (the Package Bundle)

Add a normative mechanism **Package export** to the Distribution group, beside *Package* and *Package requirement*. It says the following.

**What a package export is.** Exporting a package takes one installed package (its package manifest and the definition files the manifest lists) and writes a **Package Bundle**: a single JSON document conforming to `docs/schema/2.0/package-bundle.json` that carries definitions inline as objects, in the bundle's ten definition arrays (`fields`, `types`, `views`, `compositions`, `vocabularies`, `lifecycles`, `relationTypes`, `themes`, `blueprints`, `protocols`), together with the package's publication metadata. It is the export counterpart of package install: install consumes a bundle, export produces one. This RFC defines **whole-package export**: the export of an entire package, nothing selected out of it. The bundle-format rules ([C1] first sentence, [C2], [C4], [C5], [C6]) govern every package export; the form that synthesises a new package from selected definitions (subset export) is RFC-047's and is not accepted here.

**Which definitions: the package, then its references.** A whole-package export carries **every** definition the source package manifest lists, in every definition kind, each at the `version` its definition file carries. It then follows references, using the reference strengths the standard already declares (`rfc-decision-c8704763`, stated here so the rule is self-contained):

| Strength | What it says | Followed by export? | Reference sites in definitions |
|---|---|---|---|
| PINNED | this definition, this `version` (an `{id, version}` pair) | **Yes**, to that exact version | a `ref`-datatype Field's target Type (`ExactTypeRef`); Type inheritance (`extendsTypeId` with its version); Vocabulary and Lifecycle inheritance (`extendsVocabularyId`, `extendsLifecycleId`); a Composition's `rootTypeRefs`; a Blueprint's `rootTypes`, `requiredTypes` and `RelationSpec` source and target Types |
| LINEAGE | this definition, whatever version the context installs (a bare UUID) | **Yes**, to every version of it the exporting repository's effective package set holds | `fieldId` in a Type's field assignments, overrides, cross-field rules and `fieldOrder`; the Field ids that are the `roles` values of a View's composite-renderer binding and of a Composition's composite-renderer directive; in a View's rows, in a Composition section's `titleFieldId` and `ordering.fieldId`, in a composite-renderer directive, and in a Theme's `cssClassFields`; the View ids that are the values of a Composition section's `typeDispatch`; a Type's `identityFieldId` and `lifecycleRef`; a Field's `vocabularyRef`; a Composition section's `renderViewId`; a `typeId` in a Composition's discovery query, a Theme's record wrapper override or a Protocol's `FieldRef`; the `fieldId` of a Protocol's `FieldRef` (`/stages/*/contributesTo/*/fieldId`, target kind field); a Protocol's target and output Types |
| KEYED | whatever matches this key in the consumer's set (a string key) | **No** | `relationType` keys (in a Blueprint's `RelationSpec`, a View's relations presentation, a Type's or Lifecycle's `requires-relation` rule), lifecycle state keys, term keys, `namespace/name` keys (`typeFilter`, `typeDispatch` keys, a discovery query's `typeNamespace`/`typeName`) and a View's informational `compatibleTypes` |
| LOCATOR | where to fetch bytes, never what they mean | **No** | a Composition's `themeRef` and `themeVariants` (`ThemeReference`) |

The table is exhaustive for the definition schemas in `docs/schema/2.0/` at acceptance, and is derived by one rule: every property of a definition schema that holds another definition's UUID (bare, or as an `{id, version}` pair) is a reference site, with the strength `rfc-decision-c8704763` declares for it; a site added by a later RFC declares its strength there (the decision's cross-rule: strength is declared where the reference is defined). An empty value (a Protocol's `targetType` may be `""`) is not a reference. Not reference sites: a definition's `Lineage` provenance (`sourceDefinitionId`, `forkedFromDefinitionId`), which records history, not a dependency; and a Composition source's `containerId`/`containerIds`, which name instances' containers, not definitions. Each reference is resolved in the **exporting repository's effective package set** (the RFC-014 R6 union, with the RFC-029 core package): the set of definitions the repository itself would use. A *followed* reference is then handled by `mode`:

- **Both modes: `dependencyRefs`.** Every definition version reached by a followed reference, whether or not it is carried, is listed in `dependencyRefs` as a `Reference` (`{id, namespace, name, version, definitionType}`), one entry per `id` and `version`, **including** the source package's own definitions that other carried definitions reference (a package's own Field used by its own Type is listed). `dependencyRefs` therefore means "the definitions this package's content references", as RFC-044 [R7] defines it, not "the definitions missing from this bundle"; a listed entry that is also carried is not an unmet need. A PINNED reference reaches the one version it names, a LINEAGE reference every version of its `id` that the effective package set holds (usually one). This is what Invariants 7, 15, 35, 36, 37 and 43 require ("must appear in `dependencyRefs`"), in both modes, and what the schema says the list is for ("Consumers use this to validate completeness without parsing content internals").
- **`mode: "bundled"`** (self-contained). Every definition reached by a followed reference is carried in its kind's array, and its own followed references are followed in turn, until nothing new is reached. A Type from another package brings its Fields; a View brings its Type; a Composition brings the Views it renders; a `ref` Field brings its target Type; a Field brings its Vocabulary; a Type brings its Lifecycle.
- **`mode: "standalone"`**. Only the source package's own definitions are carried; every other definition reached is named only by its `dependencyRefs` entry, and the consumer is expected to have it installed.
- **The RFC-029 core package, in both modes (Revision 10).** A definition of the core package (`com.semanticops.core`, the package every implementation embeds, RFC-029) that is reached by a followed reference is **not** carried in the bundle's definition arrays, even in `mode: "bundled"`, and it **is** listed in `dependencyRefs` like any other reached definition version (one entry per `id` and `version`). The reference is stated, not assumed: a consumer can check from `dependencyRefs` alone that the core versions it embeds are the ones the bundle needs. The closure itself is unchanged; only what is carried differs. The exception covers definitions the export reaches from another package, never the source package's own: an export of the core package itself carries every definition its manifest lists, as [C1] requires of any whole-package export. Why this keeps the bundle portable: core is substrate, not a dependency a consumer can lack, and a core definition is identical by `id` and `version` in every implementation, so naming it preserves exactly what carrying it would; carrying it would repeat the substrate in every bundle and make every install deduplicate it.

`mode` is a choice the exporter's caller makes; an exporter that is given none uses `"bundled"`.

**What this guarantees, and what it does not.** In a bundled bundle every PINNED and LINEAGE reference resolves to a definition inside the bundle, or, for a definition of the RFC-029 core package, to its `dependencyRefs` entry; in a standalone bundle each resolves inside the bundle or to an entry of `dependencyRefs`. The Package invariants (Invariants 7, 8, 15, 35, 36, 37 and 43) check a subset of these same references, each one both listed in `dependencyRefs` and, when bundled, carried; the bundled-mode clause of Invariants 8, 15, 35, 36, 37 and 43 gains the same core-package exception at acceptance ("a definition of the RFC-029 core package is listed in `dependencyRefs` and need not be carried"); since this closure lists and (when bundled) carries every one of them, every such bundle satisfies the invariants (Invariant 8 is read, as intended, for entries with `definitionType: "field"`; its wording has no filter, which is an RFC-044-side wording note, not a rule change here). They are the checked floor, not a second closure rule. (The existing `core-bundle.srsj`, with `dependencyRefs: []`, does not satisfy them; it is not an export output, What breaks.) KEYED and LOCATOR references are **not** carried from other packages, by the strengths' own design: a relation-type key resolves against the consumer's installed relation types, and a `ThemeReference` says where to fetch a Theme, not which definition the Composition depends on. Consequence: a bundled export whose Blueprint names a custom relation type, or whose Composition points at another package's Theme (including a `ThemeReference` of mode `bundled` whose `themeId` names another package's Theme), installs cleanly, and this RFC adds no install-time check for them: an unresolved relation-type key surfaces where it is resolved, as a validation error on any relation that uses it (RFC-005 E1: a missing definition is a validation error), and an unresolvable `ThemeReference` is handled as `ext:themes-l1` handles any theme locator; the source package's **own** relation types and Themes are always carried, because every definition of the package is. What this costs: a bundled export of a small package that builds on a large one carries every definition of the large one that it reaches, and grows with it.

**When export fails.** An exporter MUST stop with a diagnostic, and write no file, when: a definition file the manifest lists is missing or does not parse; any carried definition fails its own definition schema; a followed reference does not resolve in the effective package set; two different definitions with the same `id` and `version` would be carried; or RFC-044 [R11] forbids it (a `packageDependencies` entry without `packageId`). A partial or schema-invalid bundle is never written.

**Not a repository.** A Package Bundle carries **definitions only**. It never contains records (instances), relations, source documents, a `manifest.json`, a `.srs/` marker, a root container or an `instanceIndex`. Because it has no records it has no RFC-013 root container and no identity record, so it is not an SRS repository and MUST NOT be opened, validated or navigated as one: RFC-013 does not apply to it. To move the records that use a package's types, export a container slice (RFC-026). The one non-definition content a bundle may carry is an RFC-045 `readme` (package metadata, not an instance or a source document).

**Identity and metadata.** A bundle carries two independent identity layers.

- *Package identity.* `packageId` and `packageVersion` are the source package manifest's `id` and `version`. Because `packageId` is stable across versions, a later export of the same package is the same `packageId` at a higher `packageVersion`: a consumer recognises it as an update, and RFC-014's `upstreamPackage` (whose `packageId` "never changes across upgrades") tracks it. An exporter never mints a new `packageId` for a whole-package export. The cost, stated by RFC-044 Change A: a package republished under a new `id` is a different package to every requirement that names the old one.
- *Definition identity.* Every carried definition keeps its own `id`, `namespace`, `name` and integer `version`. Export never rewrites them. A consumer deduplicates and merges definitions by `id` and `version`, whichever bundle delivered them.

Every top-level property of the bundle has one source:

| Bundle property | Source | Required in the bundle |
|---|---|---|
| `packageId`, `packageVersion`, `packageName` | the source package manifest's `id`, `version`, `name` ([C3]) | yes |
| `packageNamespace`, `packageDependencies` | the manifest's `namespace` and `packageDependencies`, as RFC-044 [R5] and [R11] state | yes |
| `schemaVersion` | the constant `"2.0"`: the SRS specification version whose `package-bundle.json` the bundle conforms to (the schema's own example value) | yes |
| `dataModelRevision` | the exporting repository's `dataModelRevision` ([C6]) | written by every export |
| `mode` | the caller (default `"bundled"`) | yes |
| `publishedAt` | the caller; an exporter that is given none uses the current time | yes |
| `publisher`, `homepage` | the caller, if given; omitted otherwise | no |
| `description` | the manifest's `description` | no (written when the manifest has one) |
| `readme` | the package directory's readme file, per RFC-045 Change B | no |
| (not carried) | the package manifest's `title`, `status`, `createdAt` and `updatedAt`, and the file paths of its definition arrays | — |
| `$schema` | the constant `https://srs.semanticops.com/schema/2.0/package-bundle.json` | written by every export |
| the ten definition arrays, `dependencyRefs` | the closure above | `fields`, `types`, `dependencyRefs` always (possibly empty); each other array only when it has at least one entry |

**The file.** A Package Bundle written to a file is one JSON document with the suffix **`.srspkg`**, the package counterpart of the `.srsj` repository file. No archive wrapper (a ZIP, a `.tar.gz` of a directory) is used: the `.srspkg` file is the distributed artifact. Tools SHOULD recognise a bundle by the `.srspkg` suffix, as `repo copy` recognises `.srsj`.

**Determinism.** The serialisation is fixed so that re-exporting an unchanged package reproduces the file and a diff between two exports shows only what changed:

1. The document is UTF-8 without a byte-order mark, and is one JSON object (RFC 8259) with no duplicate member names in any object.
2. **Every object at every depth**, the top-level object and every object inside a definition alike, writes its members in ascending order of member name, comparing names by Unicode code point (not by UTF-16 code unit, which orders characters above U+FFFF differently; a JavaScript default `sort()` is therefore not conformant for such names).
3. Arrays keep their element order, with one exception: the ten definition arrays are ordered ascending by `id` and then by `version` (numerically), and `dependencyRefs` by `id`, then `version`, then `definitionType` (an absent `definitionType` first). `id`s are compared as written, by Unicode code point, with no case folding. So the order in which a package manifest lists its files never reaches the bundle, while order inside a definition (a Type's field assignments, a protocol's stages) and the order of `packageDependencies` (which RFC-044 [R5] equates with the manifest's list) are content and are kept.
4. `fields`, `types`, `dependencyRefs` and `packageDependencies` are always written; any other definition array with no entries is not (Change C's property table), so "present but empty" and "absent" cannot both occur.
5. **Identical content** means: identical definitions (as JSON values) and identical values of every top-level property, including `publishedAt`, `publisher`, `homepage`, `description`, `mode`, `dataModelRevision` and `readme`. Given identical content, the same build of the same exporter MUST write byte-for-byte identical files on every invocation. Nothing else (file-system order, file timestamps, host, locale, environment, the wall clock when `publishedAt` is given) may change a byte.

Insignificant whitespace, a trailing newline, string-escape spelling (a raw `é` or its escape, backslash-u-00e9) and number spelling (`1` or `1.0`) are the exporter's choice, held fixed by rule 5 within one build. This is the scope RFC-017 [R6] gives the `.srs` archive. Consequence: a `.srspkg` is content-hashable per exporter build, two exports by different exporters parse to the same JSON value with the same member order, and a committed `.srspkg` changes in `git diff` only where the package changed as long as one exporter writes it. What it costs: a different exporter, or a new release of one, may rewrite every line's whitespace, and its hash differs; `publishedAt` is content, so an exporter that stamps the current time writes a new file each run. What it forecloses: byte identity across exporters, which would need a canonical-JSON profile such as RFC 8785 (resolved Open Question 2).

**Data-model revision.** A whole-package export stamps the bundle's `dataModelRevision` with the exporting repository's `dataModelRevision`. The repository's stamp is the authority: a repository at revision N loads, validates and migrates its packages as revision N (RFC-043's migration, for example, re-stamps every package manifest it touches), so the definitions an export reads from it satisfy N. A package manifest's own stamp is not consulted; it can lag (measured 2026-10-02: in `srs/srs` all 6 package manifests are stamped 8, matching the repository, while other corpora hold unstamped or older-stamped package manifests inside revision-8 repositories), and refusing on it would block exports of packages the repository already reads as current. A reader here means an implementation reading a bundle as input to package install or opening a `.srspkg`; an implementation's own embedded core package (RFC-029), which it parses as part of itself, is not a bundle read under [C6]. Such a reader treats an absent stamp as revision 0 (RFC-033 [R6]) and then:

- **Stamped above the reader's supported revision:** the reader refuses the bundle with a diagnostic naming both revisions and installs nothing.
- **Stamped below:** the reader brings the bundle to its revision through the data-model migrations' bundle-form transformers, one step at a time, before reading any definition (RFC-043 [R17] is the bundle-form transformer for revision 7 to 8). A step whose migration changes no shape a Package Bundle carries (no definition schema, no bundle property) has the **re-stamp** as its bundle-form transformer: the reader sets the bundle's revision to the step's target and continues. RFC-046's step (revision 8 to 9) is such a step: it adds `createdBy` to instances only, and RFC-046 records `package-bundle.json` as unaffected ("carries definitions, not instances"). If any step from the bundle's revision to the reader's has no bundle-form transformer, or a transformer refuses, the reader refuses the bundle with a diagnostic naming the step and installs nothing. What a transformer reports it could not carry forward (for example RFC-043's `migration-memberorder-dropped`) the reader passes on as diagnostics, and the install proceeds.
- **Equal:** read as is.

A reader never reads an older generation's definitions as if they were current; this is the bundle analogue of what Invariant I-135 requires of a record. Consequence today: the bundle-form steps specified are RFC-043's transformer (revision 7 to 8) and RFC-046's re-stamp (revision 8 to 9), so a revision-9 reader reads bundles stamped 7, 8 or 9 and refuses any bundle stamped below 7, including an unstamped (revision 0) one. Without the re-stamp rule, a revision-9 reader would refuse every revision-8 bundle, including every export of a current revision-8 repository (`srs/srs` is stamped 8). Every bundle a conforming exporter writes is stamped, so this bites only hand-made or pre-RFC bundles. The one existing bundle, `core-bundle.srsj` (stamped 2), is not read through this path: srs-rust embeds it and parses it directly as the RFC-029 core package.

**Readers: what this RFC does not add.** Beyond [C2] (never read a bundle as a repository) and [C6] (the revision gate), this RFC adds no rule for readers. How a bundle's definitions are installed (no-op on the same `id`, `version` and content; conflict on the same `id` and `version` with different content; a newer package version installed *alongside* the prior one, no record rewritten) is the existing package install contract (RFC-014 R3, R6), and RFC-044 [R9] defines the optional pre-install requirement check.

**Tooling note (informative).** srs-rust#1210 (merged 2026-10-03, srs-rust#632, #663, #690) implemented `srs package export`, the `.srspkg` reader and `package install --bundle` (CLI and WASM) while this RFC was still Draft, ahead of srs#857's sequencing. It does not yet conform to this revision; srs-rust#1212 conforms it. Measured against srs-rust `origin/master` `f0616268`: the exporter finds references by walking every string leaf for known ids (not by the reference-site table), writes `dependencyRefs: []`, lets the first package boundary win on a duplicate `id` instead of failing, stamps the binary's `CURRENT_DATA_MODEL_REVISION` (9) instead of the repository's stamp, writes `schemaVersion` from the manifest's `srsVersion` (`2.0-draft`) instead of `"2.0"`, does not sort the definition arrays by `id` then `version`, and omits `description`. It already omits core definitions from the arrays, as the core-package exception allows, but does not list them in `dependencyRefs`. Its reader refuses a bundle stamped above 9 and runs every other bundle through `migrate_package_bundle_value` (srs-rust#1158, [C6]'s 7-to-8 step, which re-stamps only a bundle that already carries `dataModelRevision`), then reads it: it does not yet refuse a bundle stamped below 7 or unstamped, as [C6] requires. srs-usage.md §5g describes the tool as shipped and points at srs-rust#1212.

## Conformance Rules

> **[C1]** A package export (whole-package now; subset export once RFC-047 is accepted) MUST be emitted as a Package Bundle conforming to `docs/schema/2.0/package-bundle.json`. A whole-package export MUST carry every definition its source package manifest lists, each at the `version` its definition file carries, and MUST resolve every PINNED and LINEAGE reference made by a carried definition (the reference sites in Change C's table) in the exporting repository's effective package set: in `mode: "bundled"` every definition so reached MUST be carried, transitively; in both modes every definition version so reached MUST be listed in `dependencyRefs`, one entry per `id` and `version`. A definition of the RFC-029 core package so reached, other than one the source package manifest itself lists, MUST NOT be carried in the definition arrays in either mode, and MUST be listed in `dependencyRefs` like any other. A PINNED reference reaches the one version it names; a LINEAGE reference reaches every version of its `id` that the effective package set holds. KEYED and LOCATOR references are not followed. An exporter MUST NOT write a bundle when any condition in Change C's *When export fails* holds.
>
> **[C2]** A Package Bundle MUST carry definitions only, plus the package metadata `package-bundle.json` declares (including an RFC-045 `readme`). It MUST NOT contain instances, relations, source documents, a `manifest.json`, a `.srs/` marker, a root container, or an `instanceIndex`. A conformant tool MUST NOT open, validate, or navigate a Package Bundle as an SRS repository — RFC-013 does not apply to it.
>
> **[C3]** For a whole-package export, the bundle's `packageId` and `packageVersion` MUST equal the source package manifest's `id` and `version`, and its `packageName` MUST equal the manifest's `name`. (`packageNamespace` and `packageDependencies` are set by RFC-044 [R5] and [R11], which take effect with this rule.)
>
> **[C4]** Every carried definition MUST preserve its original `id`, `namespace`, `name`, and `version`; definition identity MUST NOT be rewritten on export.
>
> **[C5]** A Package Bundle that a package export writes to a file MUST be a single JSON document, UTF-8 without a byte-order mark, with the suffix **`.srspkg`**, and no archive wrapper. Every object in it, at every depth, MUST write its members in ascending order of member name by Unicode code point, with no duplicate names. Arrays MUST keep their element order, except that the ten definition arrays (`fields`, `types`, `views`, `compositions`, `vocabularies`, `lifecycles`, `relationTypes`, `themes`, `blueprints`, `protocols`) MUST be ordered ascending by `id` and then `version` (numerically), and `dependencyRefs` by `id`, `version`, then `definitionType` (absent first), with `id`s compared as written by Unicode code point. `fields`, `types`, `dependencyRefs` and `packageDependencies` MUST always be written (possibly empty); any other definition array with no entries MUST NOT be written. Given identical content (identical definitions and identical values of every top-level property, including `publishedAt`), the same build of an exporter MUST write byte-for-byte identical files on every invocation, and no other input may change the output. Byte identity between different exporters is not required.
>
> **[C6]** A whole-package export (always of a package installed in a repository) MUST stamp the bundle's `dataModelRevision` with the exporting repository's `dataModelRevision`. A reader of a bundle as input to package install or of a `.srspkg` (an implementation's own embedded core package excluded) MUST treat an absent stamp as revision 0; MUST refuse, installing nothing, a bundle stamped above its supported revision; and MUST bring a bundle stamped below its supported revision forward through a bundle-form transformer for every intervening step before reading any definition from it, refusing the bundle, installing nothing, when a step has no transformer or a transformer refuses. A step whose migration changes no shape a Package Bundle carries has the re-stamp as its bundle-form transformer (RFC-046's revision 8 to 9 is such a step). Each refusal MUST be reported with a diagnostic naming the revisions or step involved.

Rule-label continuity: [C1] to [C5] keep Revision 5's labels, and the meaning RFC-044 and RFC-045 cite is preserved: [C3] still makes a whole-package export keep the package's `id` and `version` (RFC-044 [R5]'s condition), and [C5] still makes the bundle one sorted-key, byte-reproducible JSON document in which `readme` sorts like any key (RFC-045 Change B). Against Revision 5: [C2] gains the explicit `readme` exception and [C4] is unchanged; [C1]'s closure is stated by reference strength instead of a per-kind list and gains the export-failure clause and (Revision 10) the RFC-029 core-package exception; [C3] keeps only its whole-package half; [C5] is made testable; [C6] is new (Revision 10 adds its re-stamp sentence).

If the owner prefers, each `.md` takes a marked correction (`rfc-decision-4431046e`) in this RFC's fold PR; the default is no edit.

## Consistency with RFC-044 and RFC-045

- **RFC-044 (accepted, PR #860).** The bundle shape this RFC accepts is RFC-044's: required `packageNamespace` and `packageDependencies` (a local `$defs.DependencyRef` identical to the manifest's), optional `themes`, `blueprints` and `protocols`. [C1] carries every definition kind including those three. [C3] sets `packageId`, `packageVersion` and `packageName` and defers `packageNamespace` and `packageDependencies` to RFC-044 [R5] by citation, so the omission clause (an entry for a fully inlined package MAY be omitted) is stated once. [C5]'s array rule keeps `packageDependencies` in source order, because [R5] requires it to equal the manifest's list. `dependencyRefs` keeps the meaning RFC-044 [R7] gives it (definition references, not package requirements), and [C1]'s standalone clause uses it in that meaning. [C1]'s failure list includes RFC-044 [R11] (an exporter never copies a `DependencyRef` without `packageId`). The RFC-044 [R9] pre-install check of a bundle's `packageDependencies` is unaffected.
- **RFC-045 (Accepted, Revision 8, srs#858, PR #865, merged).** RFC-045 adds an optional `readme: {path, content}` to bundles and says its bundle rules take effect with this RFC. [C2] does not exclude it (a readme is not an instance, relation or source document). [C5]'s sorted-key rule orders `readme`'s two members like any other object, and "identical content" includes `readme`, which is exactly RFC-045 Change B's *Determinism* paragraph ("`readme` takes part in `[C5]`'s sorted-key serialisation like any other key"). A whole-package export is the "pack" RFC-045 [R3] and [R5] bind; a subset export, which RFC-045 [R5] calls "not the same artifact", is RFC-047's.
- **Landing order (done).** RFC-044 (#860) and RFC-045 (#865) have both merged; this fold is rebased on them and touches only description text in `package-bundle.json`.
- **RFC-046 (Accepted, srs#850, PR #861, `dataModelRevision` 9).** Adds `createdBy` to instances only and records `package-bundle.json` as unaffected, so its migration step is a re-stamp for bundles under [C6]. A bundle carries no instances and so never carries `createdBy`.

## Rationale

**Why narrow RFC-003 rather than extract the subset under a new number.** Both are precedents here (Revision 5 moved Changes E and F out to RFC-026; RFC-014 extracted a sub-scope of RFC-003 under its own number). Which side keeps the old number decides which citations stay true. The accepted subset is cited by two accepted RFCs and an implementation issue as "RFC-003 [C3]/[C5]"; the parts that move are cited only by proposal history. Keeping RFC-003 for the accepted subset keeps every standing contract literally true (axis 5–11), at the cost of a new number for the Draft remainder.

**Why the reference strengths are the closure.** Revision 5's per-kind closure list restated, in different words, part of what Invariants 7, 8, 15, 35, 36, 37 and 43 check, and had already drifted (it names `DocumentView` and `Schema`). The invariants themselves cannot be the closure: they cover Fields of Types, Types of Views, Blueprints and Protocols, Views of Compositions and base Types, and miss a `ref` Field's Type, a Field's Vocabulary and a Type's Lifecycle. Every reference a definition can make already declares its strength (`rfc-decision-c8704763`), and the strength says exactly what an export must do: a PINNED or LINEAGE reference names a definition the referrer depends on, a KEYED reference is meant to resolve in whatever set the consumer has, and a LOCATOR names bytes, not a dependency. One rule from one source; the invariants remain the check.

**Why `.srspkg` is one JSON document, not an archive.** A bundle carries only definitions and small metadata, all of it JSON; one JSON file has one hash, diffs in `git`, and needs no archive determinism rules (RFC-017's ZIP rules exist because a `.srs` must carry arbitrary source-document bytes). RFC-045 likewise carries the readme as a string inside the document for the same reason.

**Why Unicode code-point order, and why `publishedAt` is content.** Code-point order is locale-independent and is what most JSON canonicalisers use; locale collation would make the bytes depend on the host. `publishedAt` is a required property that a consumer reads; excluding it from "identical content" would let two files with different dates claim identity.

**Why every definition, not a reachable subset.** A whole-package export is the package, so it carries every definition the manifest lists, including ones nothing references (a helper Field, an unused Vocabulary). Dropping unreferenced definitions would make the export a subset under the package's own `packageId`, breaking [C3]'s update lineage.

**Why sorted keys at every depth and sorted definition arrays.** "Sorted-key" at the top level only would leave each definition's member order to the implementation, and the order of `fields[]` to the order files happen to be listed in. Both would make two exports of the same package differ for reasons that are not content.

**Why same-implementation byte identity.** It is the scope RFC-017 [R6] already chose for `.srs`, it is enough for content hashing and `git diff`, and it does not force every implementation onto one JSON writer. Cross-implementation identity is a stronger promise that nothing needs yet (resolved Open Question 2).

**Why the core package is declared, not carried (Revision 10).** RFC-029's core package is substrate every implementation embeds, identical by `id` and `version` everywhere, so carrying its definitions in every bundle adds bytes and duplicate-install work and preserves nothing a consumer could lack (Portability is met by declaration). Leaving it out silently, as the first implementation did, would make a dependency assumed rather than stated (Attribution) and drop followed references (Reference, Water's *carried, never dropped*). Listing every reached core version in `dependencyRefs` keeps all three, and the closure rule itself does not change. The geometry is in Charter alignment.

**Why a revision gate.** A bundle travels to readers older and newer than its writer. Without [C6] a newer reader would read old-shape definitions as current (the failure Invariant I-135 forbids for a corpus), and an older reader would silently misread new shapes. RFC-043 [R17] already requires bundle forms to be migrated; [C6] says when a reader must do it.

## Alternatives Considered

### Alt A — Mark RFC-003 "Accepted in part" in place

Rejected: an RFC record has one lifecycle state, `check-rfc-integration.mjs` requires the `.md` Status line to equal it and rejects a status outside the legal set, and only an `accepted` RFC carries an integration manifest. A mixed status would need a new lifecycle state and a gate change for one RFC.

### Alt B — Extract the subset into a new Accepted RFC; RFC-003 stays Draft

The RFC-014 shape. Rejected because RFC-044 [R5] and RFC-045 [R3], both owner-accepted, condition their bundle rules on "RFC-003 `[C3]`" and "RFC-003 whole-package export" being accepted; under Alt B those conditions would never literally be met and both RFCs would need a Door 3 revision to re-point them. Alt B is the owner's alternative if a new number for the accepted subset is preferred (resolved Open Question 3).

### Alt C — A decision record accepts the subset; RFC-003 stays Draft

Rejected: a decision record is rationale, not a normative home. The fold into the canonical spec is gated on an accepted RFC with an integration manifest; normative text cannot be folded under a Draft RFC.

### Alt D — Accept all of RFC-003

Rejected: Changes A, B, D and G and subset export were never reviewed against the current model (`DocumentView` and `Schema` retired, federation removed by `rfc-decision-4f1e12e5`), and nothing needs them now.

### Alt E — Keep Revision 5's per-kind closure list, or use the Package invariants as the closure

Rejected: the list restates part of the invariants and is already stale; the invariants alone miss three reference sites (Rationale).

### Alt G — Carry core definitions in bundled exports, or omit them without listing them (Revision 10)

Rejected by the owner's ruling (srs#869): carrying them repeats the substrate in every bundle; omitting them unlisted leaves the dependency assumed and the followed references dropped (Charter alignment, geometry table).

### Alt F — Cross-implementation canonical JSON (RFC 8785) now

Not taken (resolved Open Question 2): stronger than any present need, and it fixes number spelling for every implementation.

## Open Questions

**None.** All four were resolved by the owner on 2026-10-03 (Revision 10).

### Resolved

1. **The core bundle's suffix (resolved: follow-up migration).** RFC-029 and RFC-033 call the embedded core and metamodel package a "deterministic `.srsj` bundle" valid against `package-bundle.json`, but `.srsj` is the `ext:json-store` repository format and a package bundle file is `.srspkg` under [C5]. This RFC leaves the file alone ([C5]'s suffix rule binds export output only). Ruling: accept the recommendation; `core-bundle.srsj` is renamed to `core-bundle.srspkg` as a migration under `rfc-decision-628cf6c4`, with the RFC-029/033 prose corrected: srs#872 (spec side) and srs-rust#1213 (embedded asset, `core_bundle_drift` test).
2. **Cross-exporter byte identity (resolved: (a)).** Options were (a) same exporter build only, as RFC-017 [R6]; (b) require RFC 8785 (JSON Canonicalization Scheme), or pin indentation and a final newline, so any two exporters write identical bytes. Ruling: (a), as [C5] states; revisit when a second exporter or a registry `sha256` needs cross-exporter hashes.
3. **The mechanics of partial acceptance (resolved: this revision's mechanics).** RFC-003 is narrowed and Accepted; the remainder is RFC-047 (Draft), filed as srs#871, with its Draft stub record created in the acceptance PR. Alt B (a new Accepted RFC for the subset, Door 3 revisions to RFC-044 and RFC-045) is not taken.
4. **Guard the reference-site table (resolved: follow-up check).** The table is exhaustive by the derivation rule, checked by hand at Revision 9 against every `format: uuid` and `{id, version}` property of the ten definition schemas. Ruling: accept; a `scripts/checks.json` check that fails when a definition schema gains such a property not named in the *Package export reference sites* mechanism record (`mechanism-64469ada`) is srs#873.

Closed in Revision 7: the Theme closure question (Revision 6 OQ2) is settled by the strength rule: a `ThemeReference` is a LOCATOR and is not followed, and a package's own Themes are always carried.
