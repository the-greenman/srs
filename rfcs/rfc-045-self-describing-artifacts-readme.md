- The `.srs` ZIP and RFC-038 [R10]: a `.srs` already carries files at their paths, and [R10] already preserves application content. This RFC adds no `.srs` mechanism; it only says that a `.srsj` readme becomes an ordinary entry when converted to a `.srs` (Change C).

**Layer test:**
- Which layer owns this? The *carriage* (`readme` on `package-bundle.json` and `srsj-envelope.json`) is MEANING plane substrate: the `docs/schema/2.0` carrier schemas of the package-distribution and `ext:repository` machinery. The readme *content* is outside the semantic model, in the same position as an opaque source payload under RFC-038: carried, preserved, never parsed. Producing and consuming travelling forms is OPERATION plane, core service; identifying which file is the readme and displaying it are tooling and client concerns (Tooling conventions). The compass's source-of-truth map has no row for artifact prose and needs none: this RFC creates no home for meaning, only a carrier for text that has none.
- Consume or clone downward? Consume. `readme.path` is a plain relative path within the artifact, the form `PackageRef.path` and `StylesheetDeclaration.path` already use; it is not a new reference strength and not a LOCATOR (`rfc-decision-c8704763`'s LOCATOR may point outside; this may not).
- Does the layer below stand alone without this? Yes. Delete every `readme` property and every package, repository, bundle and archive stays valid, loadable and semantically identical; [R1] guarantees nothing depends on it.

**Level test (`rfc-decision-c20fcff8`):** Each rule passes: a travelling form declares `readme`, and an implementation can check the path and content rules, the carriage, the restoration and the keep-on-rewrite rule against it. What fails the test (which file is the readme, whether a `.srs` producer includes one, what to write in it, which editors to suggest) is written as non-normative Tooling conventions, never as conformance rules.

## Abstract

A package or repository may have a readme (prose that explains it), but the single-file travelling forms drop it: a package bundle (`.srspkg`) and a `.srsj` archive are JSON documents with no place for a Markdown file. This RFC lets each of them carry one readme as `readme: {path, content}`, the file's actual path within the artifact and its text, so that unpacking restores it under the same name and a tool that rewrites the travelling form keeps it. The `.srs` ZIP already carries files at their paths, and a readme in one is ordinary application content that RFC-038 already preserves. The spec does not require a readme, does not name one, does not say how a tool finds it, and derives nothing from its content: if it is bundled, it is kept.

### What you commit to, and what this forecloses

- **Committed:** a bundle and a `.srsj` may carry one readme as its actual path plus its UTF-8 text; whoever unpacks writes it at that path without overwriting anything; whoever rewrites the bundle or `.srsj` (or converts a `.srsj` to a `.srs`) keeps it unchanged unless the user removes or replaces it.
- **Committed:** two diagnostics, `readme-invalid` (error, for a bad path, un-encodable text, or a readme over an implementation's size limit; the readme is then neither written nor carried) and `readme-write-conflict` (warning). Absence of a readme is never an error or a warning.
- **Not committed, and left to tooling:** any default file name; how a tool picks the readme from a directory or from a `.srs`; whether a `.srs` producer includes one; scaffolding; display.
- **Foreclosed for now:** a `.srsj` carries the repository's readme only, never local package readmes (Alt E); a readme whose bytes are not UTF-8 is never carried in the JSON forms; a readme at a non-conventional path is found again after a trip through a directory or a `.srs` only if the tool is told where it is (Alt B, Change C).
- **Cost:** a strict reader that predates this RFC refuses a bundle or `.srsj` that carries a readme. Because the reference tools' conventional repository readme is the "About SRS" file every new repository gets, clients must advance their srs-rust pins before they consume `.srsj` archives packed by a build that picks it up (What breaks).

## Motivation

### Problem 1 — Authored prose is lost on the first pack

A README beside a package's `package.json`, or in a repository, is application content under RFC-038: not discovered, not validated, not modified, and not carried. A package bundle (`.srspkg`) is a single sorted-key JSON document (RFC-003 `[C5]`) with no file tree and no property for prose; a `.srsj` archive's `data` map holds only parsed JSON files (`srsj-envelope.json`: *"to that file's parsed JSON content"*; in `gallery.srsj` all 87 entries are JSON objects). So any readme an author writes is lost the first time the artifact is packed into either form, which is the failure `rfc-decision-8948e43f` names: *"A capability that exists only in place is captivity."* The muDemocracy.org#242 editor-install work makes this concrete: package bundles are about to become the way packages move between repositories, and a package's explanation of itself should arrive with it.

### Problem 2 — A file that travels must say what it is called

A JSON travelling form has no file name of its own for anything it inlines. If a readme is carried as text only, the unpacker must invent a name, and two unpackers can invent different ones; a readme that was `docs/overview.md` comes back as something else. The owner's ruling says the bundled readme must therefore record its actual filename.

### What this RFC does not do

It does not require a readme, define where one lives, define how a tool recognises one, or give its content any meaning. Every one of those was in Revisions 1 to 3 and was removed by the owner's final ruling; the tooling side of them is in Tooling conventions, as implementation guidance.

## Proposed Changes

### Change A — The bundled readme: one shape

A **bundled readme** is an object with exactly two properties, both required:

| Property | Type | Meaning |
|---|---|---|
| `path` | string | The readme's actual path within the artifact it describes, as the producer found it: relative to the package directory (the directory holding `package.json`) for a package bundle; relative to the repository root (the directory holding `manifest.json`) for a `.srsj`. Examples: `README.md`; `docs/overview.md`; `.srs/README.md`. |
| `content` | string | The file's text: its bytes decoded as UTF-8 and otherwise unchanged. Line endings and any byte-order mark are carried as characters, so writing `content` back as UTF-8 reproduces the file's bytes. |

No other property is allowed (`additionalProperties: false`). The shape is defined once and used under the property name `readme` on both JSON travelling forms (Changes B and C).

**What a readme is, for this RFC.** A readme is whatever text file the producer carries in this property. The spec does not say how a producer chooses it (that is tooling's job; the conventions are in Tooling conventions) and does not require one to exist. A travelling form without `readme` is complete and conformant.

**The content is opaque.** No implementation may derive validity, identity, lifecycle state, relations, membership, ordering or any other model fact from it. It is not validated as Markdown or CommonMark, not compared with `description`, the identity record or any record, and not size-limited by this RFC; an implementation that needs a size limit applies its own behind the axis 3–9 local boundary, and reports an over-size readme as `readme-invalid` (below), never dropping it silently. If a readme and the records disagree, the records are right and no tool will notice. The only checks this RFC allows on `content` are that it can be written back as UTF-8 (below), an implementation's own size limit, and, when writing, whether an existing file already holds the same bytes ([R6]).

**Content rule.** A JSON string can contain an unpaired surrogate escape (for example `"\ud800"`), which is not a Unicode character and cannot be encoded as UTF-8. `content` must contain none: it must be a sequence of Unicode scalar values. A `content` that breaks this rule is the error `readme-invalid` (below). Many JSON parsers (srs-rust's `serde_json` among them) reject such an escape for the whole document; for those, the travelling form is unreadable as malformed JSON, like any other malformed JSON, and `readme-invalid` does not arise. The rule applies to implementations whose parser accepts the escape.

**Path rules.** `path` must be a non-empty relative path written with `/` separators:
- not absolute: no leading `/`;
- no `\` and no `:` anywhere (a `:` makes `C:` or `C:foo` a drive or drive-relative path on Windows, and names an alternate data stream on NTFS);
- no empty, `.` or `..` segment (so no `//` and no trailing `/`), and no segment ending in `.` or a space (Windows strips those, so `records./x.md` would alias `records/x.md`);
- no control character (U+0000 to U+001F, or U+007F).

Together with the write rule below (which refuses to write through a symbolic link), these rules make the path safe to write: it can only name a location inside the artifact. No Unicode normalisation is applied. The exclusions below are compared ASCII-case-insensitively (so `Records/x.md` and `MANIFEST.JSON` are excluded too, because on macOS and Windows file systems they would land in `records/` or on `manifest.json`); everything else about `path`, including what is carried and restored, is exact. A path that a particular file system cannot hold (too long, or a parent that is a regular file) is the write conflict below, not a path error.

In addition the path must not name a file the format already gives a role:
- in a package bundle: it must not be `package.json`;
- in a `.srsj`: it must not be `manifest.json` or `.srs` itself, must not equal any key of the envelope's `data` map, must not lie inside one (`x.json/README.md` when `x.json` is a key) and must not be a proper ancestor of one (`themes` when `themes/a.json` is a key), and must not equal or lie inside any of these reserved repository locations of RFC-038 [R5]: `records`, `notes`, `typed-records`, `relations`, `containers`; the directory named by the envelope manifest's `sourceDocumentsPath` (`source-documents` when absent); the path named by the envelope manifest's deprecated `changelogPath` when present; and every local package root, meaning the root itself when `package.json` is a key of `data`, and every directory `D` such that `D/package.json` is a key of `data`. Every one of these is decided from the envelope alone. A manifest-supplied path is compared after removing a leading `./` and any trailing `/` (so `./attachments/` excludes `attachments/x.md`). RFC-038 [R5] also lists `federationPath` and `federationEventsPath`; they cannot occur in a revision-8 envelope (`ext:federation` was removed and the envelope's manifest is closed), and if they return they join this list. The `.srs` directory is allowed because its contents are implementation-private under RFC-038 [R5], so an implementation that keeps its readme there may carry it; local package roots are excluded because the `.srsj` readme is the repository's, not a package's (*Local package readmes*, Change C), and because a file there would be a package's application content, not the repository's.

These rules are checked by implementations when reading a travelling form, not by the JSON Schema: most depend on the rest of the envelope, which a schema cannot see, and the syntactic ones would need regular-expression lookaheads that not every schema validator supports (Schema changes). So a form can be schema-valid and still carry an invalid readme.

**An invalid readme.** A `readme` whose `path` breaks a path rule, whose `content` breaks the content rule, or which exceeds an implementation's size limit, is the **error** `readme-invalid`. The diagnostic names the travelling form, the `readme.path` value as given, and which rule failed. The readme is not written anywhere and is not carried into any travelling form written from this one; the rest of the load, unpack or rewrite proceeds, and the travelling form is otherwise read normally. Like every validation diagnostic, it is reported in the command's diagnostics and counted among its errors; it does not by itself make a command fail (the CLI contract: exit code 0 means the command ran). A path that passes these rules can still meet an existing file when written (for example on a case-insensitive file system); that is the write conflict below, not an invalid readme.

**Writing it out, and never overwriting.** An implementation that writes a travelling form out, as files or as a `.srs` archive, distinguishes two kinds of file: **carried** files, which come from the travelling form (its `data` entries, its definitions, its readme), and **generated** files, which the implementation adds on its own account (a marker placeholder such as `.srs/.gitkeep`, an "About SRS" scaffold, any other default it writes). The readme is a carried file, and it is kept as follows:
- **Generated files never take its place.** An implementation MUST NOT write a generated file at a carried readme's `path`, on a file system or as an archive entry. If it would otherwise write one there (for example its own `.srs/README.md`), the carried readme is the file at that path instead.
- **Written last among carried files.** On a file system, the readme is written after every other carried file of the operation, encoding `content` as UTF-8 at `path` relative to the directory being written (the package directory, or the repository root), creating any missing parent directories. In a `.srs` archive, it is one regular-file entry at `path` (Change C).
- **Never over anything that is already there.** If any file or directory already exists at that path (an entry that was there before the operation, or a carried file the same operation wrote), or the readme cannot be written there for any other reason (a parent that is a regular file, a name the file system cannot hold), or any component of the path, including the last, is a symbolic link, the implementation leaves what is there unmodified, does not write the readme, reports the warning `readme-write-conflict` naming the path, and completes the rest of the operation. There is no diagnostic when the existing entry is a regular file whose bytes equal the UTF-8 encoding of `content`. The one exception is an explicit user instruction to replace the existing file (for example an upgrade the user asked to refresh the readme), in which case the implementation writes over it (still never through a symbolic link).

Writing it last among carried files makes the outcome deterministic: the readme never displaces a file the format gives a role, and loses only to carried files or pre-existing entries. For a `.srsj` the carried paths are fixed by the envelope, so the outcome is the same on every implementation; for a bundle, whose definition file names the writer chooses (Change B), it is the same given the same chosen names. Refusing symbolic links keeps a write into an existing directory inside the artifact. This applies `rfc-decision-2e0cd70a`'s "refuse loudly on write" to one file rather than to the whole operation.

**Keeping it: "if it exists, we keep it".** An implementation that reads a travelling form carrying a valid `readme` and writes a travelling form of the same artifact from it carries the readme unchanged, path and content, unless the user explicitly removes or replaces it. "The same artifact" means a re-export or re-pack, an upgrade or migration that rewrites the bundle or envelope, and a conversion from a `.srsj` to a `.srs` (where the readme becomes an entry at `path`, Change C). A new artifact made from part of one (a subset package export under RFC-003, a slice under RFC-026) is not the same artifact, and this rule does not bind it. This is the rule that turns "allowed" into "kept": without it, any tool that round-trips an artifact without knowing about readmes would silently drop one.

The rule binds only where the input marks a readme, which a bundle and a `.srsj` do and a `.srs` does not. A `.srs` read as input has no `readme` property, so nothing in it is "the readme" for this rule; its readme file is an ordinary entry, kept by RFC-038 [R10] (Change C). When a `.srsj` is written from a `.srs`, which file becomes its `readme` is the producer's choice (Tooling conventions), exactly as when it is written from a directory.

**Producing it.** A producer that carries a readme carries the text of a regular file inside the artifact, never a symbolic link and never a file reached through a symbolic link, and never a file whose bytes are not valid UTF-8. The path it records must satisfy the path rules above. A file it cannot carry is simply not carried (a `.srs` can still hold it as an ordinary entry); how the producer tells the user, if at all, is tooling's choice.

### Change B — Package bundle (`.srspkg`)

`package-bundle.json` gains one optional property, `readme`, holding a bundled readme (Change A) whose `path` is relative to the package directory.

- **Pack (whole-package export).** A producer that carries the package's readme sets `readme` to its path and content. A bundle has room for one readme, and it is the exported package's own: a `mode: "bundled"` bundle inlines its dependencies' *definitions* (`[C5]`), not their readmes. This RFC requires nothing of a subset export (RFC-003: a new package with a newly minted `packageId`); what readme, if any, it carries is its producer's choice.
- **Unpack and install.** An implementation that writes the bundle out as a package directory (an unpack, or an install that writes a package directory into a repository) writes the readme at `path` in that directory under Change A's write rule. The bundle's definitions carry no file names, so the writer chooses those; because the readme is written last, a definition file the writer chose at the same path wins and the readme is reported as a write conflict. An install that keeps the package in some other form (a database, an in-memory model) should keep `readme` with the installed package, so that a later whole-package export of that package carries it. This is a SHOULD, not a MUST, because the spec defines no data model for an installed package outside a directory.
- **Determinism.** `readme` takes part in `[C5]`'s sorted-key serialisation like any other key; its members are carried unchanged, so byte-for-byte reproducibility is preserved. A bundle that carries a readme is a different byte sequence, and so has a different digest, from the same package's bundle without one.
- **Links.** A readme's relative links to other files in the package directory are not preserved by a bundle, which carries no other files. The text survives unchanged; what it links to may not exist after unpack. Authors who need durable links use absolute URLs (Tooling conventions).

**Terms.** To **pack** is to produce a travelling form from an artifact: a package bundle from a package directory (RFC-003's whole-package export), or a `.srsj` / `.srs` archive from a repository. To **unpack** (or **materialise**) is to write a travelling form back out as files. RFC-003 defines export and install; it does not define writing a bundle out as a directory, so the unpack rule binds only implementations that offer that operation.

**Effective date.** RFC-003 is Draft, and its whole-package export is put up for acceptance separately (srs#857). Everything this RFC says about bundles (the bundle half of [R2], [R3], and [R4]–[R6] as they apply to bundles) takes effect when RFC-003's whole-package export is accepted. This RFC is accepted before that, as RFC-044 was for its own bundle producer clause; until then `readme` is a valid optional bundle property that nothing requires anyone to write or read. srs-rust has no third-party bundle reader yet (srs-rust#632); when it ships one, these rules bind it. The `.srsj` rules take effect at acceptance.

### Change C — Repository archives (`.srsj`, `.srs`)

**`.srsj`.** `srsj-envelope.json` gains one optional top-level property, `readme`, holding a bundled readme (Change A) whose `path` is relative to the repository root. It is the repository's readme. It sits beside `data`, not inside it: `data` is defined as parsed JSON keyed by path, and a Markdown file is not JSON (Rationale). On unpack it is written under Change A's write rule; on any rewrite of the envelope it is kept (Change A).

**`.srs`.** The deterministic ZIP (RFC-017) already names every entry by its path, so a readme needs no property and no schema change: it is one more entry, and its entry name is its actual path. A `.srs` marks nothing as "the readme", and none of this RFC's rules bind a `.srs` producer that packs a repository directory: whether it includes the readme file is a tooling convention (RFC-038 [R17] requires the six authoritative sets, the manifest and the marker, not application content). Once a readme file is in a `.srs`, it is ordinary application content: a file under no reserved repository location (Change A's path rules keep a carried readme out of them) or inside `.srs/`, which RFC-038 [R10] and [R5] already say MUST be preserved unmodified by any repository operation, and which [R17] says a consumer discovers by the same rules as a live repository. This RFC adds nothing to those rules.

**Converting between forms.**
- *`.srsj` to `.srs`:* the `.srs` includes the readme as the one regular-file entry at `readme.path` (Change A, *Keeping it*); a converter that adds its own `.srs/` files does not add one at that path (Change A, *Generated files never take its place*). RFC-017's determinism rules ([R5], [R6]) apply to it like any other entry.
- *`.srs` (or a repository directory) to `.srsj`:* the producer chooses which file, if any, becomes `readme`, by its own convention or the user's choice. A readme at the conventional path (Tooling conventions) is found again; one at a non-conventional path (`docs/overview.md`) survives as an ordinary file in the `.srs` and in any directory it is unpacked to, but is not carried in the new `.srsj`'s `readme` unless the user points the tool at it. This is a stated cost of the ruling's no-declaration scope (Alt B), with the same return trigger.

**Local package readmes.** A repository archive can contain local packages, each of which may have its own readme. A `.srs` holds such a file as ordinary application content at its path (RFC-038 Change D: at a local package root, only `package.json` and the declared definition paths are candidates; other files are application content), kept by RFC-038 [R10]. A `.srsj` does not carry it: its `readme` is the repository's only, and a package's own travelling form is its bundle (Change B). This is a deliberate limit of the minimal scope: carrying several readmes in a `.srsj` would need a list and a rule saying which is which, and no consumer needs it yet. The return trigger is a `.srsj` consumer that needs a package's readme without a `.srs` or a bundle.

**Slices (RFC-026).** A slice is a new artifact made from part of a repository, in one of the forms above. A slice in `.srsj` form may carry a readme, under the same shape and rules; this RFC does not say which readme a slice should carry, and [R5] does not oblige a slice to carry its source's readme.

## Conformance Rules

Diagnostic codes defined by this RFC: `readme-invalid` (error) and `readme-write-conflict` (warning). Each is reported in the operation's diagnostics with the travelling form or target path it concerns; neither aborts a load, pack or unpack.

> **[R1]** An implementation MUST NOT derive validity, identity, lifecycle state, relations, membership, ordering or any other model fact from the content of a bundled readme. It MUST NOT validate that content as Markdown or any other format, and MUST NOT compare it with any record, `description` or identity record. The only checks it MAY make on `content` are [R2]'s content rule, [R6]'s byte comparison, and an implementation-defined size limit, whose violation it MUST report as `readme-invalid` under [R4] and never handle by silently dropping the readme. A travelling form without `readme` is conformant, and an implementation MUST NOT report the absence of a readme as an error or a warning.
>
> **[R2]** `package-bundle.json` and `srsj-envelope.json` MAY carry `readme`, an object with exactly two required string properties: `path` and `content`. `path` is relative to the package directory in a package bundle and to the repository root in a `.srsj`. `content` is the file's bytes decoded as UTF-8 with no other change, and MUST consist only of Unicode scalar values (no unpaired surrogates). A producer MUST NOT set `readme` from a file whose bytes are not valid UTF-8, from a symbolic link, or from a file reached through a symbolic link, and MUST record a `path` that satisfies [R4].
>
> **[R3]** *(Effective with RFC-003 whole-package export, srs#857.)* An implementation that writes a package bundle carrying a valid `readme` out as a package directory MUST write `content`, encoded as UTF-8, to `path` relative to that directory, subject to [R6]. An implementation that installs such a bundle without writing a package directory SHOULD retain `readme` with the installed package so that a later whole-package export of that package carries it.
>
> **[R4]** A `readme.path` MUST be non-empty, MUST use `/` as separator, MUST NOT begin with `/`, MUST NOT contain `\`, `:` or any character U+0000 to U+001F or U+007F, and MUST NOT contain an empty, `.` or `..` segment or a segment ending in `.` or a space. In a package bundle it MUST NOT be `package.json`. In a `.srsj` it MUST NOT be `manifest.json` or `.srs`, MUST NOT equal, lie inside, or be a proper ancestor of a key of `data`, and MUST NOT equal or lie inside `records`, `notes`, `typed-records`, `relations`, `containers`, the envelope manifest's `sourceDocumentsPath` (`source-documents` when absent) or its `changelogPath` when present (each compared after removing a leading `./` and any trailing `/`), or any local package root (the root itself when `package.json` is a key of `data`; every directory `D` such that `D/package.json` is a key of `data`). The exclusions in the two preceding sentences are compared ASCII-case-insensitively; there is no Unicode normalisation. A `readme` that violates [R4], [R2]'s content rule (where the implementation's JSON parser accepts the document at all) or an implementation's size limit MUST be reported as an error with code `readme-invalid`, naming the travelling form, the `path` value and the rule broken; it MUST NOT be written anywhere and MUST NOT be carried into any travelling form written from this one; and the load, unpack or rewrite MUST otherwise proceed.
>
> **[R5]** An implementation that reads a package bundle or `.srsj` carrying a valid `readme` and writes a travelling form of the same artifact from it (a re-export or re-pack, any rewrite by an upgrade or migration, or a conversion from `.srsj` to `.srs`) MUST carry the readme with `path` and `content` unchanged, unless the user explicitly instructs it to remove or replace the readme. In a `.srs` the readme is carried as a regular-file entry at `path`. A new artifact made from part of one (an RFC-003 subset export, an RFC-026 slice) is not the same artifact.
>
> **[R6]** An implementation that writes a carried readme out, to a file system or as a `.srs` archive, MUST NOT write any file it generates on its own account (a marker placeholder, a scaffold) at the readme's `path`. On a file system it MUST write the readme after every other carried file of the same operation, creating missing parent directories, and MUST NOT write it over any existing file or directory, nor through a symbolic link at any component of `path`, unless the user explicitly instructs it to replace that file (and never through a symbolic link). When a component of the path is a symbolic link, or, absent such an instruction, an entry exists at the target path and is not a regular file whose bytes equal the UTF-8 encoding of `content`, or the readme cannot be written there for any other reason, it MUST leave what is there unmodified, MUST report a warning with code `readme-write-conflict` naming the path, and MUST complete the rest of the operation.

**Conformance fixtures (tooling, no door).** The reference implementation's follow-up (srs-rust#1164) carries fixtures for at least:
- `readme-invalid`, nothing written, nothing carried on rewrite: a `path` with `..`; an absolute path; `C:/x`, `C:foo` and `docs/x:y`; a `\`; an empty segment; a control character; a segment ending in `.` or a space; a `.srsj` `path` of `.srs`, of `Records/x.md`, inside a `data` key (`x.json/README.md`) and an ancestor of one; a `.srsj` `path` of `manifest.json`, of a `data` key, of `records`, under `records/`, and under a local package root; a `content` with an unpaired surrogate escape (for a parser that accepts the escape; a parser that rejects it reports malformed JSON).
- Valid: a `.srsj` `path` of `.srs/README.md`; a package bundle `path` of `docs/overview.md`.
- Manifest-supplied locations: a `sourceDocumentsPath` of `attachments` (a readme under `attachments/` invalid, under `source-documents/` valid), and of `./attachments/` (same result).
- Round trips preserving `path` and `content` byte-for-byte, including CRLF line endings and a byte-order mark: bundle → bundle, `.srsj` → `.srsj`, `.srsj` → `.srs` (entry present at `path`), and a `.srsj` → `.srs` conversion whose converter would otherwise generate its own `.srs/README.md`, for a carried readme at `.srs/README.md` (exactly one entry, the carried text). The further leg `.srs` → `.srsj` re-identifying `.srs/README.md` tests the tooling convention, not this RFC, and lives in srs-rust#1164's tooling tests.
- Writing: an unpack over an existing file with identical bytes (no diagnostic), with different bytes (`readme-write-conflict`, file unchanged), and with an explicit replace instruction (file replaced); an unpack where another carried file of the same operation has the readme's path (that file kept, `readme-write-conflict`); an unpack whose implementation would generate a file at the readme's path (the carried readme written, nothing generated there); an unpack into a directory where a parent of `path` is a symbolic link (`readme-write-conflict`, nothing written through it), and where a parent of `path` is a regular file (`readme-write-conflict`).

The srs repository adds no checker for this RFC beyond the deep-equality assertion in Schema changes.

## Schema changes

| Schema file | Change | Effect on existing data |
|---|---|---|
| `package-bundle.json` | Add optional `readme` (`$ref: #/$defs/BundledReadme`). Add `$defs.BundledReadme`: object, `additionalProperties: false`, `required: [path, content]`, both plain strings. The `$def`'s descriptions are form-neutral ("relative to the root of the artifact this form carries") and state that the path and content rules are checked by implementations, not by this schema; the per-form anchor (package directory, or repository root) is in the description of each schema's `readme` property. Not added to the top-level `required`. | None. The one bundle in the corpus (`core-bundle.srsj`) carries no `readme`. |
| `srsj-envelope.json` | Add optional top-level `readme` (`$ref: #/$defs/BundledReadme`) and the same `$defs.BundledReadme`. Not added to `required`. The envelope's other `$defs` are unchanged. | None. The 5 envelope instances (`gallery.srsj` and the four governance seed `.srsj` files, 1.0.0, 1.1.0, 1.2.0 and 1.2.1) carry no `readme` and stay valid. |
| `generation-ledger.md` | The `package-bundle.json` row records this RFC's hand patch; the `srsj-envelope.json` row records the new Field and value-object Type. | None. |

`package-manifest.json` and `manifest.json` do **not** change: there is no readme declaration (Alternatives, Alt B).

**No `pattern` on `path`.** The schema types `path` and `content` as plain strings. The contextual path rules (`data` keys, reserved locations, local package roots) cannot be expressed in a schema that sees one property, and the syntactic ones would need negative lookahead, which ECMA-262 has but the regular-expression engines behind some JSON Schema validators (for example Rust's `regex` crate) do not. Putting half the rules in the schema would make "schema-valid" look like "valid readme" when it is not. [R4] is enforced by implementations.

**Hand-authored or generated.** Per `docs/schema/2.0/generation-ledger.md`:
- `package-bundle.json` is **hand-authored** (out of the #272 Type-modelling scope) and takes a hand patch. Its `$defs.BundledReadme` is a local copy, following the self-contained-schema practice RFC-044 used for `DependencyRef` and `blueprint.json`/`composition.json` use for `ExactTypeRef`.
- `srsj-envelope.json` is a **generated row**: hand-maintained and loaded as committed, but closure-proven against the metamodel Type `srsj-envelope` by `rfc-534-closure-test.mjs` (emitter ⊆ committed seed; the seed already carries `$defs` for the Types it references, such as `ContainerEntry` and `Manifest`, and `BundledReadme` is added the same way). So `scripts/gen-metamodel-package.mjs` gains, in the same change:
  - a value-object Type `bundled-readme`, the next Type ordinal (77) under the generator's append-only numbering, whose assignments are the **existing** Fields `path` (required) and `content` (required); the form-neutral descriptions live only in the two hand-authored `$defs` (identical, so the copy check passes), as `ContainerEntry`'s do today, because the closure test strips `description` before comparing and the generator needs no `FieldAssignment` descriptions;
  - a new Field `readme`, the next Field ordinal (278), `ref` to `bundled-readme`, `inline`, `single`, assigned optionally to `srsj-envelope`;
  - the `srsj-envelope` Type's description extended with one clause for `readme`;
  - the `path` Field's description generalised from *"Relative path to a referenced file (a package directory/package.json, or a Theme JSON file)"* to *"Relative path to a file within the artifact that holds it"*, which is what it already means in its current assignments to `AssetDeclaration` and `StylesheetDeclaration`. Its value domain (a string) does not change.

  All metamodel Fields and Types stay at version 1: the generator hardcodes `version: 1`, and the metamodel package is excluded from `check-versioning-cell.mjs` as a regenerated bootstrap fixed point (`rfc-decision-991c062f`). The generated package regenerates with `gen-metamodel-package.mjs` and the `com.semanticops.spec/generated-type-reference` record for `SrsjEnvelope` with `scripts/gen-type-reference-tables.mjs`, never by hand, and `rfc-534-closure-test.mjs` must stay green.
- **Copy check (tooling, no door).** RFC-044 created `scripts/check-package-bundle-alignment.mjs`, which asserts among other things that the two `$defs.DependencyRef` copies are deep-equal (RFC-044, *New check*, item (b)). This RFC adds one assertion to it: the two `$defs.BundledReadme` copies are deep-equal.

**Order with RFC-044 (srs#855).** RFC-044 patched `package-bundle.json` (`packageNamespace`, `packageDependencies`, `$defs.DependencyRef`, `themes`, `blueprints`, `protocols`), its ledger row, and created the alignment check. RFC-044 Revision 3 leaves readmes out of scope for this RFC (its *Self-description* paragraph). **RFC-044 landed first** (merged in #860); RFC-045's patch is rebased onto it as a pure addition of one optional property and one `$def`, its ledger row text is appended to RFC-044's, not replaced, and its copy assertion is added to the existing script. The property names are disjoint, and `readme` is not a definition kind, so RFC-044 [R6] (every definition-kind property of the manifest has an array of the same name in the bundle) is unaffected; `package-manifest.json` is not touched, so `check-schema-kind-correspondence.mjs` needs no new row.

Schema changes must be synced to:
- `srs-rust/crates/srs-schema/schemas/2.0/` (via `scripts/check-schema-sync.sh`)
- `srs-vscode/schemas/2.0/` (manual copy)

## What breaks

**Nothing becomes invalid.** Both added properties are optional, no existing property changes, and no existing artifact carries `readme`. Measured on 2026-10-02 against srs `origin/master` `6bc3a71`, and re-checked unchanged at `51496ea` (after RFC-044 and RFC-046 merged): 1 package bundle (`core-bundle.srsj`) and 5 `.srsj` envelopes, none carrying `readme`; no file anywhere is renamed, moved, required or reinterpreted. The two known `.srs/README.md` files (srs's `docs/spec/examples/gallery-project-v2/.srs/README.md`, and srs-programme's) are unaffected by the spec: it gives them no role.

**Spec prose.** At fold, the *Package* and *ext:json-store* mechanisms and the `ext:repository` extension record gain this RFC's rule text (Affects, fold map). The *Repository layout* mechanism's existing sentence (*"by convention `.srs/README.md`, an* About SRS *orientation document"*) is not changed.

**Readers that predate this RFC.** Both touched schemas are closed at their top level (`additionalProperties: false`), so an artifact that *uses* `readme` is rejected loudly by a strict pre-RFC reader, never silently misread:
- A strict JSON Schema validator of either form reports the artifact invalid.
- srs-rust's `.srsj` envelope reader is `deny_unknown_fields`, so a build before the one that ships this RFC refuses a `.srsj` carrying `readme` outright. The clients pinned to such a build are srs-web (its bindings, `scripts/ensure-bindings.mjs`), muDemocracy.org (its CLI pin, `scripts/ensure-srs-cli.mjs`) and srs-vscode (its bundled CLI).
- srs-rust's only bundle reader today (`core_package.rs`, for the embedded core bundle) does not deny unknown fields; `.srspkg` export and install are not yet shipped (srs-rust#632), so no pinned client reads third-party bundles yet.

**Which artifacts will carry a readme, in practice.** Nothing in this RFC makes a producer add one, so the refusal applies only to artifacts that actually carry a readme, and none do today. But the reference tools' convention (Tooling conventions) treats `.srs/README.md` as the repository readme, and that is the same file `rfc-decision-1967b8eb` part (3) makes the conventional "About SRS" member of `.srs/`, which `repo create` will scaffold (srs-rust#1066). So once srs-rust#1164 ships the conventional pick-up, every `.srsj` packed from a repository that has `.srs/README.md` carries `readme`: today the 2 repositories above, and after srs-rust#1066 every newly created repository. A client pinned to an earlier srs-rust build refuses those archives. This is accepted, not avoided: the About file is exactly the orientation prose this RFC exists to carry, and choosing a different file would put a second readme convention beside the first. The choreography that handles it is the usual one: the spec PR merges, the mirrors refresh, srs-rust ships reading support no later than the pick-up, and srs-web, muDemocracy.org and srs-vscode advance their pins before they consume `.srsj` archives packed by a build with the pick-up. A `.srs` needs no new reader: its readme is an ordinary entry.

**The About file stays the implementation's.** [R5] binds only a rewrite from one travelling form to another. Packing from a directory reads the file as it is there, so a tool that refreshes its own About text in a repository has the new text carried the next time the repository is packed. Only a rewrite of an existing `.srsj` (with no directory involved) keeps the older text, unless the user asks to replace it. And when a `.srsj` that carries `.srs/README.md` is unpacked, the carried text is what lands there, not the tool's default About text (Change A, *Generated files never take its place*).

**Rendered output and navigation:** unchanged; 0 records, relations or containers change.

### Migration decision: no `dataModelRevision` bump

`dataModelRevision` (RFC-033) stamps a data-model generation that an engine must gate on because existing data has to change shape. Nothing here migrates: no existing data changes, both additions are optional, and an absent `readme` means exactly what it meant before. `dataModelRevision` therefore stays at 8. The strict-reader rejection above is the closed-schema contract working as `rfc-decision-2e0cd70a` intends (*"the validation complaint IS the louder diagnostic"*); a revision bump would instead make every old binary refuse every new corpus, including all the ones that carry no readme. RFC-044 reached the same conclusion for its additive change.

## Tooling conventions (non-normative)

This section is implementation guidance. It fails the level test (it can be followed but is not checked against any declaration), so it adds no conformance requirement, and an implementation that does otherwise is conformant. It records what the reference tools are expected to do so that they agree with each other.

- **Which file is the readme.** Tools conventionally treat `README.md` in the package directory (beside `package.json`) as a package's readme, and `.srs/README.md` (the "About SRS" file of `rfc-decision-1967b8eb` part 3) as a repository's readme. The repository convention sits inside `.srs/` because a repository root is often also a source-control root whose own `README.md` describes the hosting project (in srs, the root `README.md` is about the GitHub project, while the SRS repository is `srs/srs/`). A tool MAY let a user choose a different file; whatever it chooses, it records the actual path in `readme.path`.
- **Pack.** `pack` (package export, `.srsj` and `.srs` archive) picks up the conventional file when it exists, is a regular file and is valid UTF-8, and records its path and text. A `.srs` pack includes the repository's application content, including the readme file. Pack does not synthesise a readme when there is none.
- **Create.** `package create` and `repo create` MAY scaffold a short readme at the conventional location (for example a heading with the title and the description). For a repository this is the natural discharge of the `.srs` non-emptiness convention's "About SRS" member (`rfc-decision-1967b8eb` part 3), which that decision leaves to the implementation (srs-rust#1066).
- **Display.** Clients (srs-web, srs-vscode) MAY show a readme: a package's in package pickers and install prompts, a repository's on its landing view. A client that renders it treats it as untrusted CommonMark: it executes nothing, sanitises raw HTML or shows it as text, and resolves relative links against the readme's own directory.
- **Agents.** The MCP server and the agent index MAY expose the repository readme (and local package readmes), for example as a resource beside `srs://<repositoryId>/map`. They present it as untrusted prose, never as the repository's identity or purpose, which remain the identity record's.
- **Authoring.** Lead with why the artifact exists and who it is for (the `description` already says what it is); give a worked example; suggest editors and tools in prose ("open the decision records in srs-web's decision editor"), since the spec defines no editor concept (compass layer rule 6); prefer absolute URLs, because a bundle carries no other files; do not restate the records.

Follow-up issues, each a sub-issue of the-greenman/muDemocracy.org#242:
- **srs-rust#1164**: carriage in the core (pack/unpack/install of `.srspkg`, `.srsj` and `.srs` per [R2]–[R6], the two diagnostics, the fixtures above), the conventional pick-up (shipped no earlier than reading support), `package create` / `repo create` scaffolding (coordinated with srs-rust#1066), and exposure through MCP and the agent index.
- **srs-web#355**: display of package and repository readmes, under the rendering guidance above.
- **srs#859**: `srs-usage.md` documents the conventions and the carriage for agents.

## Rationale

**Only the travelling forms.** A readme in a package directory or a repository already exists as a file; nothing in the spec needs to know about it there. The loss happens only when the artifact becomes a single JSON document, so that is the only place the spec acts. The `.srs` ZIP already names files and RFC-038 [R10] already keeps application content, so a `.srs` needs nothing new.

**Record the path, not a declaration.** The owner ruled that a bundled readme records its actual filename. Recording it in the travelling form (rather than declaring it in `package.json` or `manifest.json`) is sufficient for the guarantee that matters: whatever the producer carried in a bundle or `.srsj` is restored under the same name and kept on every rewrite. Which file a producer picks in a directory or a `.srs` is tooling's job (Alt B).

**`path` and `content`.** `path`, not `fileName`, because the value can contain directory segments (`.srs/README.md`, `docs/overview.md`), and the metamodel already calls a relative in-artifact location `path` (`PackageRef.path`, `StylesheetDeclaration.path`, theme asset `path`). `content`, not `text`, because `text` is the metamodel's name for a `TextSegment`'s raw stored value, while `content` is its generic "free text content" Field. Reusing both is *one name over many*; the `path` Field's description is generalised to say what its existing assignments already use it for.

**One object, not two flat properties.** `readme: {path, content}` keeps the two values that only mean something together in one place, makes "no readme" a single absent property rather than two that could be half-present, and gives both JSON forms one shape (and one `$def` the copy check compares).

**Beside `data`, not inside it.** `data` is defined as parsed JSON keyed by path. A string value under a `.md` key would pass the schema (the map is open), but an existing materialiser would write a JSON string literal into the file: quoted, with escaped newlines. A new top-level property is rejected loudly by those same readers instead. Loud over silent.

**The keep rule ([R5]) is the ruling.** "If it exists, we will keep it" is not satisfied by allowing the property: a tool that rewrites an envelope or re-exports a bundle without knowing about readmes would drop it silently. [R5] makes keeping it a conformance requirement on every writer of a travelling form whose input marks a readme. It cannot bind a `.srs` input, which marks none; there RFC-038 [R10] keeps the file, and only its role as "the readme" depends on tooling.

**An invalid readme is dropped, loudly.** A readme with an unsafe path or un-encodable text cannot be written, and carrying it forward would hand the same error to every later reader. Reporting it as an error and not carrying it is the loud outcome; the rest of the artifact is unaffected because the readme carries no model meaning.

**Carried beats generated; readme written last among carried files.** An implementation may generate its own files when it unpacks (srs-rust writes `.srs/.gitkeep` today, and srs-rust#1066 will scaffold `.srs/README.md`, the conventional readme path). If a generated file could take the readme's place, the author's readme would be replaced by default text on every unpack, which is exactly the loss this RFC exists to prevent; so generated files yield. Among carried files, writing the readme last means it can never occupy a name the format needs (on a case-insensitive file system, `MANIFEST.JSON` before `manifest.json`), and the outcome is the same on every implementation. Refusing symbolic links keeps an unpack into an existing directory from writing outside it.

**UTF-8 text only.** A JSON string holds text, not bytes, so the carriage guarantee is text-exact: a UTF-8 file round-trips to identical bytes, and a non-UTF-8 file is not carried in `readme` rather than carried in an encoding no consumer could read. A `.srs` still carries such a file byte-for-byte as an ordinary entry.

**No synthesis.** The owner's ruling is that existence is not enforced. Synthesising a readme where none exists would add a file the author never wrote to every travelling form, and would make every new bundle and `.srsj` unreadable to pinned pre-RFC readers, including those of repositories with no About file.

## Alternatives Considered

### Alt A — Carry text only (`readmeText`), write it to a fixed name on unpack (Revisions 1–3)

Rejected by the owner's ruling: a bundled readme must record its actual filename. A fixed name on unpack also renames any readme that was not at the default, and requires the spec to name a default file, which this revision no longer does.

### Alt B — An optional `readme` path declaration on `package.json` and `manifest.json`

Declaring which file is the readme would let a non-conventional readme (say `docs/overview.md`) be found again after a bundle or `.srsj` is unpacked into a directory, or converted to a `.srs`, and packed again. Rejected under the ruling (*"unless strictly needed to identify which file is the readme for bundling"*): it is not strictly needed. Within a bundle or `.srsj` the readme is identified by `readme` itself; within a directory or a `.srs`, identification is tooling's job, and a tool may keep its own setting. The cost is stated: a non-conventional readme survives every bundle and `.srsj` round-trip and the conversion to `.srs` ([R5]), and is restored at its path, but a tool that re-packs a `.srsj` from the directory or the `.srs` using only the convention will not pick it up again. The file itself is not lost; its role as the readme is. The return trigger is a reported loss of that kind.

### Alt C — Put the readme as a string inside `.srsj` `data`

Rejected: silent corruption by existing materialisers (Rationale).

### Alt D — Carry the readme as a sibling file next to the `.srspkg`

Rejected: RFC-003 `[C5]` makes a bundle a single JSON document, which is what lets it be fetched, hashed and installed as one thing. A sibling file is lost by any channel that moves one file.

### Alt E — Carry every local package readme in a `.srsj` (a `readmes` list)

Deferred, not rejected: it needs a list and a rule for which entry is the repository's, and no consumer needs it yet; a `.srs` and each package's own bundle already carry those files (Change C, *Local package readmes*).

### Alt F — A typed record (a "readme" Type) in the model

Rejected: a repository already has its typed self-description (the identity record, RFC-013), a package cannot hold records (RFC-038 [R3]), and a readme is meant to be readable without SRS tooling.

### Alt G — Rewrite relative links on pack, or inline linked images

Rejected: it makes the readme generated rather than authored, makes pack depend on parsing Markdown, and breaks byte-identical round-trips.

### Alt H — A different conventional repository readme than the About file

Rejected (as a tooling choice, recorded here because it drives a cost in What breaks): pointing the convention at a file other than `.srs/README.md` would keep newly created repositories' `.srsj` archives free of `readme` for a while, but it would give a repository two orientation files for one purpose, against *one name over many*, and the About file is exactly the prose this RFC exists to carry. The pin choreography handles the reader cost.
